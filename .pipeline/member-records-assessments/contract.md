# member-records/assessments · contract (E25–E30)

Spec: `docs/specs/member-records/assessments.md` v2 (incl. build clarifications D1–D21) + `api-contract.md` v1 (BR-REC-153…162).
Descriptors: `backend/src/routes/assessments.ts` (notes repeat the rules below); schemas: `backend/src/types/assessments.types.ts`; tables `assessments`,
`measurements` (`data-model.md`). Generated: `backend/.contracts/*`, `frontend/src/types/api.generated.ts`.

## All six endpoints
- Base `/api`. Success `{ success: true, data }` (E27 adds `meta { page, pageSize, total, totalPages }`). Status **200 on all six**, E26 too when it creates. Error `{ success: false, message, code, details? }`.
- All `any-authenticated`. No `Idempotency-Key` on any (BR-REC-156 lists E17, E22 only); a retry of E26 is the same upsert (D6).
- Check order: Origin (403 `CSRF_ORIGIN` on E26, E29, E30) → auth (401) → params / query / JSON body shape (400 `INVALID_JSON` / `VALIDATION_ERROR`, `details.issues[{ path, message }]`, path dot-joined e.g. `values.1.value`) → handler.
  So a bad body, query or id is 400 even when the member or assessment does not exist.
- Ids are any 8-4-4-4-12 hex uuid: malformed → 400; well-formed but unknown → 404 (E25, E26, E28–E30) or an empty list (E27).
- The API says `date`; the columns are `assessments.assessed_on` and `measurements.measured_on`. Durations are whole seconds, weights kg (BR-REC-153); values come back as JSON numbers.

## Request limits (exact)
| Field | Used by | Limit | Issue `path` · `message` |
|---|---|---|---|
| `date` | E25 query, E26, E29 | a real day `YYYY-MM-DD`: `2026-02-30`, `2025-2-3`, `""`, a number fail. No range at shape level (future / before join date are service matters) | `date` · "Use YYYY-MM-DD" or "Not a real calendar date" |
| `isEstimated` | E26 (required), E29 (optional) | boolean | — |
| `values` | E26 | array of 0 to 60 entries; `[]` and all-`null` are NOT shape errors (service: `NO_VALUES`) | `values` · "Use at most 60 values" |
| `values[i].metricId` | E26 | uuid; no id twice in one body (compared ignoring letter case) | `values.<i>.metricId` of each repeat · "List each measurement once" |
| `values[i].value` | E26 | key required; number or `null`; finite; −999,999,999.999 to 999,999,999.999, bounds included (`1000000000`, `-1000000000` fail; `"2:02"`, a missing key, `1e999` fail) | `values.<i>.value` · "Use a number up to 999,999,999.999 either way" (type errors: Zod's message) |
| body of E29 | E29 | `{ date?, isEstimated? }`, unknown keys rejected (`memberId`, `typeId`), ≥ 1 field, `null` refused (BR-REC-157) | `""` · "At least one field is required" |
| `memberId` | E27 | required uuid | — |
| `typeId` | E27 optional; E25 required | uuid | — |
| `page`, `pageSize`, `sortDir` | E27 | `page` ≥ 1 (1); `pageSize` 1–100 (10); `sortDir` `asc` \| `desc` (default `desc`). There is no `sortBy`; unknown query keys are ignored | — |

Unknown body keys are ignored on E26 (only update bodies reject them). **Service checks** (400 `VALIDATION_ERROR`, path `values.<i>.value`, only for non-null entries, they need the metric's datatype):
| Check | Message |
|---|---|
| Time (`duration`) measurement: the value as sent is within 0 to 35,999 (`-0.4` and `35999.5` fail; `MAX_DURATION_SECONDS`) | "Use 0 to 35,999 seconds" |
| Number measurement: the rounded form stays within ±999,999,999.999 (`999999999.6` on a 0-decimal measurement rounds past it; refused, never a database error) | same text as the shape limit |

## Response shapes (plain)
- `entryFormSchema` `{ member{ id, fullName, joinedOn }, type{ id, name }, existing{ assessmentId, isEstimated, values{ [metricId]: number } } | null, metrics[{ id, name, unit, datatype, decimals, better, plausibleMin|null, plausibleMax|null, previous{ value, on, isEstimated } | null }] }`.
- E26 `{ assessmentId, created, saved, removed }` · E27 item `{ id, typeId, typeName, date, isEstimated, valueCount }` · E28 / E29 `{ id, memberId, typeId, typeName, date, isEstimated, values[{ metricId, name, unit, datatype, value }] }` · E30 `{ removed }`.

## Behaviour a test can rely on
**E25 entry form (BR-REC-20, 81; D1, D4, D5)**
- `existing` = the assessment of this member + type on exactly `date`, else `null`; its `values` hold every stored value (on or off measurements). A future `date` is fine (200); an off assessment and an archived member work.
- `metrics` = the type's turned-on measurements (assessment on) plus any measurement, on or off, that holds a value in `existing`, in one list in setup order (`sort_order`, then id). Assessment off and no `existing` → `metrics: []`.
- `previous` = for that measurement, the stored value with the latest date **strictly before** `date`, from any assessment of the member; `on` is its date, `isEstimated` its assessment's flag. Back-fill: values on 2025-09-30 and 2026-03-01, form date 2025-12-30 → previous is the 2025-09-30 one; a value on `date` itself is never `previous`. None → `null`.
**E26 save (BR-REC-12, 19, 76–78, 83, 86; D1–D4, D6)**
- Order after the shape check: 404 (unknown member or type) → 400 `DATE_IN_FUTURE` → 400 `METRIC_NOT_IN_TYPE` → 400 `VALIDATION_ERROR` (service checks above) → 400 `NO_VALUES`. Tests trigger one error at a time. A refused save changes nothing, `isEstimated` included.
- `DATE_IN_FUTURE`: `date` later than gym "today" (`gym_settings.timezone`; tests compute it with `gymToday(new Date(), tz)`). Today passes; no lower bound (before the join date saves).
- `METRIC_NOT_IN_TYPE`: any entry (also a `null` one) whose metric belongs to another type or does not exist. Off measurements and an off assessment are accepted.
- `NO_VALUES` (D2): the save would leave the assessment with no stored value: a NEW assessment whose `values` is empty or every `value` null; or an EXISTING one where the `null` entries remove every remaining value (use E30 to remove it). An existing assessment with `values: []` is fine (only `isEstimated` changes; `saved: 0`, `removed: 0`, `created: false`, still one `assessment.save` change-log row); sending only some of its measurements is fine (the others stay untouched).
- First save of a member + type + date → `created: true`; a second save (same or other values) → 200 `created: false`, still ONE assessment row and one `measurements` row per measurement. Two parallel saves → one row, one `created: true`, no 500 (D6).
- A measurement left out is untouched. `{ value: n }` sets it (`saved` counts every non-null entry, even an unchanged one); `{ value: null }` deletes the stored value (`removed` counts only those that existed). `isEstimated` always replaces the stored flag.
  Example: stored Weight 95.5, Plank 122; body `[Weight 94, Plank null, Waist null]` → Weight 94, Plank gone, `saved: 1`, `removed: 1`.
- Rounding (`roundMetricValue`, half away from zero, the measurement's current `decimals`): Number 95.56 @1 → 95.6, −2.25 @1 → −2.3; Time 122.4 → 122, 122.5 → 123; E28 then returns the rounded number.
- Written in one transaction under the member-row lock; `measurements.member_id` and `measured_on` copy the assessment's member and date (BR-REC-166).
**E27 list (BR-REC-89; D10)**
- Sorted by `date`, `desc` by default; same-date rows (different types) are ordered by `id` (tests use distinct dates). `typeId` filters; `valueCount` = stored values. `meta.total` counts after the filter; page past the end → `data: []`, `totalPages` ≥ 1.
- A member with no assessments, an unknown `memberId` or an unknown `typeId` → 200 `data: []`, `meta.total: 0`, `totalPages: 1` (no 404). `pageSize=500`, a missing / malformed `memberId`, `sortDir=sideways` → 400.
**E28 / E29 / E30 (BR-REC-87, 88, 92; D8, D9)**
- E28 lists every stored value (on and off measurements) in setup order. Unknown id 404, malformed 400.
- E29 `{ date }` moves the assessment and all its values' `measured_on` in one transaction (E28, E25 `previous` and E16 `lastAssessedOn` follow); `{ isEstimated }` alone leaves date and values. Same date as it has → 200 (not taken). Another assessment of the same member + type on that date → 409 `ASSESSMENT_DATE_TAKEN`, nothing changes (another type or member on that date is no conflict). Future date → 400 `DATE_IN_FUTURE`; before the join date saves. Order: 404 → `DATE_IN_FUTURE` → 409. `{}`, an unknown key, `date: null` → 400.
- E30 deletes the assessment and its values (`removed` = their number); then E28 and a second E30 are 404, E25 `existing` is `null` for that date and `E16.lastAssessedOn` / due dates read the remaining rows. Hard delete is intended (BR-REC-165).
**Change log (BR-REC-92, 158; D7)** — one `audit_log` row per successful write in the same transaction, none for a refused one: E26 `assessment.save` (create or edit, also a repeat), E29 `assessment.move` (also when only `isEstimated` changed), E30 `assessment.delete`.
`entity` `assessment`, `entityId` = the assessment id, `session_id` = the token's `sid`. `before` / `after` are full snapshots `{ date, isEstimated, values: { [metricId]: number } }`: create has `before: null`, delete has `after: null`; an edit holds the whole stored state before and after.

## What other streams and tests may rely on
- Schema names: `entryFormQuerySchema`, `entryFormSchema`, `saveAssessmentBodySchema`, `saveAssessmentResultSchema`, `assessmentListQuerySchema`, `assessmentListItemSchema`, `assessmentDetailSchema`, `updateAssessmentBodySchema`, `deleteAssessmentResultSchema`, `assessmentIdParamsSchema`; constants `MAX_VALUES_PER_SAVE` 60, `MAX_MEASUREMENT_VALUE`, `MAX_DURATION_SECONDS` 35,999. Frontend: `API_ROUTES.MEMBERS.ENTRY_FORM`, `API_ROUTES.ASSESSMENTS.{LIST,SAVE,DETAIL}`.
- E26, E29, E30 are the only writers of `assessments` / `measurements` (setup tests and seeds insert rows directly). After each write `measurements.member_id` / `measured_on` equal the assessment's `member_id` / `assessed_on`, and an assessment made through E26 holds ≥ 1 value.
- E16 `lastAssessedOn` (`membersSql.lastAssessedOn`) and the due list (E31 / E32) read `assessments.assessed_on` directly: a save, move or delete shows at once (BR-REC-88), no cache. Report card and progress (E35–E37) read `measurements`; values are stored rounded (decimals changes later never touch them, setup C9); durations are whole seconds.

- **No screen for E29** (D21): the form reaches About-only edits through E26 with an empty `values` list; `useUpdateAssessment` exists but nothing calls it yet.
- **S11:** assessment filter chips (All + turned-on assessments) kept in `?type=`, rows newest first (date or "≈ Dec 2025", assessment, "15 results"), 25 per page + "Show more"; `?open=<assessmentId>` or a row tap opens one `ResponsiveSheet` (values with units, Edit, Delete; Delete's confirm is a second step inside the same sheet, never a second sheet, #18).
- **Errors:** every server code through `messageForCode`; `NO_VALUES`, `DATE_IN_FUTURE` next to the Save bar / date field; `ASSESSMENT_DATE_TAKEN` as the BR-REC-87 sentence with an "open it" action; a failed Save (network, timeout, 5xx) keeps the form and shows "Not saved — check the connection and tap Save again" (BR-REC-86).
- **Cache (performance BR-REC-144, tactic 7/8):** entry-form query `staleTime: 0` (previous values must be fresh); lists use the app default; no optimistic updates for saving results. Every successful write (E26, E29, E30) invalidates `assessmentKeys.all`, `memberKeys.all` (`['members']`, for `lastAssessedOn`) and the key prefix `['due']` — the due-list stream (E) must root its query keys at `'due'` so BR-REC-88 "due dates update at once" holds (contract note for stream E).
- **Draft store:** `localStorage` through the pure functions below with the real `window.localStorage` (wrapped in try/catch; private mode or blocked storage = no drafts, form still works).
